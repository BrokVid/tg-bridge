# Архитектура

## 1. Роль в инфраструктуре

```
+------------------+   HMAC-запрос    +-----------------+   HTTPS    +------------------+
|  ваши серверы    | ---------------->|   Tg Bridge     | ---------> | api.telegram.org |
|  (любой хост)    | <----------------|  (публичный VPS)| <--------- |                  |
+------------------+    ответ         +-----------------+            +------------------+
        ... любые другие клиенты той же фермы ...
```

Tg Bridge — **stateless reverse-proxy**, специализированный под Telegram Bot API.
Он не хранит сообщения, не имеет БД и не знает бизнес-логику клиентов. Его
единственная работа: принять подписанный запрос → проверить авторизацию →
переслать в Telegram → вернуть ответ. Всё состояние — конфиг и секреты.

## 2. Ключевые проектные решения

### ADR-1: Rust, а не Python/Go/Node

Критерий заказчика: минимальный CPU и RAM на VPS.

| Вариант | RAM в простое | Задержка p99 | Комментарий |
|---|---|---|---|
| **Rust (axum+tokio)** | ~5–10 МБ | единицы мс | один статический бинарник, нет GC |
| Go (net/http) | ~15–25 МБ | сопоставимо | тоже неплохо, но больше RSS |
| FastAPI/uvicorn | ~80–150 МБ | выше | интерпретатор, лишние зависимости |
| nginx/openresty + lua | ~20 МБ | низкая | сложно выразить HMAC-логику чисто |

Rust даёт предсказуемую задержку без пауз GC и бинарник, который просто
копируется на сервер. Для прокси это идеальный профиль нагрузки: почти вся
работа — I/O, CPU почти не тратится.

### ADR-2: HTTP API с HMAC вместо gRPC/WebSocket

Рассматривались варианты:

1. **HTTP REST + HMAC-SHA256** ← выбрано
2. gRPC (tonic) — типизированные схемы, но тяжёлый тулинг для клиентов
   (ради пары вызовов пришлось бы ставить protobuf-стек на каждый сервер)
3. WebSocket-туннель — хорош при тысячах сообщений/сек; тут десятки в сутки
4. SOCKS5/HTTP-прокси «вслепую» — клиенту пришлось бы держать bot token,
   что размазывает секреты по всей ферме (отвергнуто)

REST+HMAC: вызывается из `curl`, Python `requests` за 10 строк, легко
дебажить, тривиально ограничивать. При этом протокол остаётся «своим»:
каждый инстанс определяет своих клиентов, их секреты и допустимые методы.

### ADR-3: Bot tokens живут только на мосте

Клиент обращается к токену **по алиасу**: `/v1/t/{alias}/{method}`. Мост
подставляет реальный токен из своего конфига. Следствия:

- компрометация клиента не раскрывает токен бота;
- ротация токена не требует правок на клиентах;
- один бот может обслуживать несколько проектов через разные алиасы.

### ADR-4: Два режима вызова

1. **Passthrough** `/v1/t/{alias}/{method}` — тело запроса уходит в Bot API
   как есть (JSON или multipart с файлами). Максимум гибкости — любой метод.
2. **Действия (actions)** `/v1/a/{name}` — именованные шаблоны из конфига:
   клиент шлёт `{"title": "...", "text": "..."}`, мост сам собирает
   `sendMessage` с нужным chat_id и parse_mode. Удобно для уведомлений:
   клиент вообще не знает про Telegram-специфику.

Оба режима опциональны per client (`allow_passthrough`, `actions`).

### ADR-5: Без базы данных

Состояние не нужно: rate limit — in-memory скользящее окно, метрики — счётчики
процесса. Перезапуск теряет только окно rate-limit'а, что безопасно.

### ADR-6: Webhook-релей без очередей

Telegram может пушить апдейты на `POST /webhook/{alias}`; мост проверяет
`X-Telegram-Bot-Api-Secret-Token` (constant-time) и доставляет апдейт на URL
клиента, подписанный HMAC-протоколом с секретом этого клиента — симметрично
обычному направлению. Очередь сознательно не строится (stateless, ADR-5):
недоставка = 502, и Telegram сам ретраит апдейты. Взаимоисключаемость
getUpdates/webhook остаётся на совести оператора бота (стандартное поведение
Bot API).

## 3. Компоненты

| Компонент | Ответственность |
|---|---|
| `server` | axum-роутер: `/healthz`, `/metrics`, `/v1/t/:alias/:method`, `/v1/a/:name`, `/webhook/:alias` |
| `auth` | проверка HMAC-подписи, timestamp-окна, IP allowlist |
| `proxy` | пул соединений к api.telegram.org, таймауты. Без авторетраев: повторяет клиент (см. PROTOCOL.md «Идемпотентность и повторы») |
| `actions` | рендер шаблонов действий из конфига |
| `config` | TOML + env-интерполяция (`env:VAR`, `file:/path`) |
| `limits` | per-client rate limit, лимит тела запроса |

## 4. Поток запроса

1. Клиент: `POST /v1/t/mybot/sendMessage`, заголовки `X-TgB-Client`,
   `X-TgB-Timestamp`, `X-TgB-Signature`; тело — JSON Bot API.
2. Мост: клиент существует? IP разрешён? timestamp в окне ±60 c?
   HMAC-SHA256(secret, `{timestamp}\n{raw_body}`) совпадает (constant-time)?
3. Rate limit по клиенту.
4. Мост берёт токен алиаса `mybot`, шлёт `POST https://api.telegram.org/bot{token}/sendMessage`.
5. Ответ Telegram (статус + JSON) возвращается клиенту дословно.

Оверхед моста сверх сети: один HMAC (~микросекунды) и одна аллокация буфера.

## 5. Безопасность

- Транспорт: ожидается размещение в приватной сети (Tailscale/WireGuard) либо
  TLS от nginx/caddy перед мостом. Протокол рассчитан на то, что тело читает
  только владелец канала, но HMAC защищает и от подделки.
- Replay: timestamp ±60 c + in-memory nonce-кэш по подписи (включён по
  умолчанию, отключается конфигом; см. PROTOCOL.md «Replay-защита»).
- Подпись сравнивается constant-time (`subtle`).
- Секреты: env или файлы с правами 0600; в логи не пишутся никогда.
- Логируем факт запроса, клиент, метод, статус, длительность — но не тело.

## 6. Что сознательно НЕ делаем

- Очередей/retention сообщений: клиент сам решает, повторять ли отправку.
- Веб-интерфейса: конфиг-файл достаточен.
- Мультиарендности «как SaaS»: модель — один хозяин фермы хостит мост для
  своих же серверов.
