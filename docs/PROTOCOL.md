# Протокол Tg Bridge (wire protocol v1)

Каждый инстанс моста определяет собственных клиентов, их секреты и права —
«свой порт, свой протокол авторизации, свой набор данных» из коробки.
Ниже — единый формат запросов, который реализует любой инстанс.

## Общие положения

- Транспорт: HTTP/1.1 или HTTP/2. Размещение — приватная сеть (Tailscale,
  WireGuard) или TLS-фронт (nginx/caddy). Голый HTTP наружу не предназначен.
- Тело запроса: JSON (`Content-Type: application/json`) для обычных вызовов
  либо `multipart/form-data` для отправки файлов через passthrough.
- Все ответы моста — дословный ответ Telegram Bot API (тот же статус-код и
  тело), либо собственная ошибка моста в формате ниже.

## Аутентификация

Каждый запрос подписывается HMAC-SHA256 общим секретом клиента.

Заголовки:

| Заголовок | Значение |
|---|---|
| `X-TgB-Client` | имя клиента из конфига моста |
| `X-TgB-Timestamp` | Unix time в секундах на момент отправки |
| `X-TgB-Signature` | hex(HMAC-SHA256(secret, string_to_sign)) |

Строка для подписи (`string_to_sign`):

```
{timestamp}\n{raw_request_body}
```

где `raw_request_body` — точные байты тела (клиент обязан подписывать те же
байты, что отправляет; никакой канонизации JSON).

Проверка на мосте:

1. клиент известен;
2. IP источника входит в `allowed_ips` клиента (если задан);
3. `|now - timestamp| <= 60` c (окно настраивается);
4. подпись совпадает (constant-time сравнение);
5. пара `(client, signature)` не встречалась в окне защиты от replay
   (см. «Replay-защита» ниже).

Ошибка 401 с телом:

```json
{"ok": false, "error_code": 401, "description": "tgb: bad signature"}
```

## Replay-защита

Подпись уникальна для пары (timestamp, body), поэтому мост ведёт in-memory
кэш увиденных пар `(client, signature)`. Повтор байт-в--байт того же запроса
в пределах окна (`2 × timestamp_window + 5 c`) отклоняется:

```json
{"ok": false, "error_code": 401, "description": "tgb: replay detected"}
```

Легитимный ретрай всегда пересоздаёт запрос с новым timestamp — модуль
`tgbridge_client.py` так и делает. Кэш включён по умолчанию, отключается
`[server] replay_protection = false`. Состояние не переживает рестарт;
после него экспозицией остаётся только окно timestamp.

## Эндпоинты

### GET /healthz

Без аутентификации. `200 {"status":"ok","version":"..."}` — для мониторинга.

### POST /v1/t/{alias}/{method}  — passthrough

Прозрачный вызов метода Bot API. `{alias}` — алиас бота в конфиге моста,
`{method}` — метод Bot API (`sendMessage`, `getMe`, `answerCallbackQuery`, …).

Пример (тело подписано как есть):

```json
{"chat_id": 123456789, "text": "deploy finished", "parse_mode": "HTML"}
```

Мост выполняет `POST https://api.telegram.org/bot{token}/{method}` и
возвращает ответ Telegram без изменений (включая `429 Too Many Requests`
и поле `retry_after` — клиент сам решает, повторять ли).

**Файлы**: тело с `Content-Type: multipart/form-data` пересылается дословно
(байты и заголовок Content-Type с boundary сохраняются) — так работают
sendPhoto, sendDocument и прочие загрузки. Подпись считается по сырым байтам
тела так же, как для JSON. На multipart действует отдельный лимит размера
(`max_upload_bytes`, по умолчанию ~50 МБ — лимит Bot API на файл).

### POST /v1/a/{action}  — именованное действие

Шаблон действия задаётся в конфиге моста (глобальный массив `[[actions]]`,
каждое действие привязано к одному клиенту). Клиент шлёт только семантические
поля, Telegram-специфика остаётся на мосте:

```json
{"title": "backup", "text": "disk 91%", "level": "warn"}
```

Мост подставляет поля запроса в `params` шаблона (`{{field}}`, с фолбэком
`{{field|default}}`; поле без значения и без дефолта — 400 со списком
недостающих полей) и отправляет сконфигурированный метод Bot API.
Ответ — нормализованный:

```json
{"ok": true, "telegram_ok": true, "result": {...}}
```

Неизвестное действие — 404; действие чужого клиента — 403;
ошибка рендера — 400.

### GET /metrics

Prometheus text format, защищён той же HMAC-подписью (заголовки как у
обычного запроса, тело пустое). Отдаёт агрегаты по всему мосту:
`tgb_requests_total{client,kind,status}`, `tgb_request_duration_milliseconds_{count,sum}`,
`tgb_upstream_errors_total`. Можно отключить: `[metrics] enabled = false`.

## Лимиты

| Параметр | Значение | Источник |
|---|---|---|
| макс. тело запроса к мосту | 64 КБ (по умолчанию) | конфиг моста |
| макс. multipart-загрузка | ~50 МБ (по умолчанию) | конфиг моста + Bot API |
| окно timestamp | ±60 c | конфиг моста |
| окно replay-кэша | 2×окно + 5 c | производная от окна timestamp |
| rate limit | per client, напр. 120 req/min burst 20 | конфиг моста |
| таймаут до Telegram | 35 c (должен быть > long-poll клиента) | конфиг моста |
| текст `sendMessage`/`editMessageText` | 1–4096 символов | Bot API 10.2 |
| подписи медиа (`caption`) | 0–1024 символа | Bot API 10.2 |
| `answerCallbackQuery.text` | 0–200 символов | Bot API 10.2 |
| `setMyCommands.commands` | не более 100 команд | Bot API 10.2 |
| `getUpdates.limit` | 1–100 | Bot API 10.2 |

Мост проверяет лимиты длины для действий (`/v1/a/*`) и возвращает понятный
400 до обращения к Telegram; passthrough пересылает как есть — ошибки
лимитов вернёт сам Telegram.

Превышение rate limit — 429:
`{"ok": false, "error_code": 429, "description": "tgb: rate limited"}`.

## Валидация ввода (мост)

- Сегменты пути `alias`, `method`, `action` — только `[A-Za-z0-9_-]`,
  длина ≤ 64; всё прочее — 400 до какой-либо авторизации.
- Заголовок подписи длиннее 128 символов — 401 без попытки декодирования.
- Арифметика timestamp — без переполнения (экстремальные значения дают 401).
- Повтор запроса с той же подписью внутри окна replay-кэша — 401.
- JSON действия парсится с защитой от глубокой вложенности (serde_json
  recursion limit) → мусорный ввод даёт чистый 400.
- `chat_id` и другие критичные параметры действий задаются на мосту;
  шаблонизация клиентских полей в `chat_id` логируется как предупреждение.

## Идемпотентность и повторы

Мост ничего не кэширует и не повторяет мутирующие методы автоматически.
Клиентам рекомендуется повторять с экспоненциальной задержкой при сетевых
ошибках и уважать `retry_after` из ответа Telegram (поле
`result.parameters.retry_after`). Модуль `tgbridge_client.py` делает это сам.

## Заметки по Bot API (сверено с официальными доками, API 10.2)

- Имена методов регистронезависимы; все запросы в UTF-8.
- `getUpdates` не работает, пока выставлен webhook (взаимно исключают друг
  друга); offset = последний `update_id` + 1; обновления хранятся ≤ 24 ч.
- Ответ Telegram всегда содержит `ok`; при ошибке — `description`,
  `error_code` и опционально `parameters.retry_after`.
- Файлы отправляются multipart-запросом через passthrough; лимит загрузки
  бота — ~50 МБ на файл. Скачивание файлов (getFile → file_path) клиент
  делает напрямую с api.telegram.org по HTTPS.

## Версионирование

`/v1/` — версия протокола. Несовместимые изменения пойдут в `/v2/`;
`/v1/` сохраняется минимум год после выхода v2.
